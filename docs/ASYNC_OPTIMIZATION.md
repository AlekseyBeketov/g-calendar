# Оптимизация асинхронных операций

## Согласованный порядок

1. Применять результат точного проверочного чтения сразу, общую сверку выполнять в фоне.
2. Выполнять независимые чтения с общим пределом четыре запроса, обновлять затронутые списки и календари.
3. Хранить несколько календарных недель и предзагружать соседнюю после текущего диапазона.
4. Уменьшить повторную подготовку данных календаря и работу интерфейса при прокрутке.

После отправки этих изменений в main реализовать собственные Google REST/OAuth в отдельной ветке. Полное авторизованное сравнение провести после настройки пользователем Desktop OAuth client. Computer use не применяется.

## Корректность

Точный GET и журнал неоднозначных записей остаются обязательными. Проверенная запись применяется по составному ключу списка/календаря и ресурса; перенос может изменить ID задачи. Неподтверждённая запись не меняет снимок.

Результат фонового чтения принимается единственным владельцем состояния. Устаревшее чтение не должно перезаписывать проверенное изменение ни в памяти, ни на диске. После изменения во время чтения требуется повторная сверка. Обязательные области сверки объединяются; переход между неделями не должен вытеснить обновление задач.

Частичная сверка не является полной синхронизацией и не разрешает удаление локальных напоминаний на основании отсутствующих в ней задач. Страницы одной коллекции читаются последовательно, разные коллекции — независимо. Ошибка чтения сохраняет последний подтверждённый кэш.

Календарный кэш ограничен числом диапазонов, различает часовые пояса и состав календарей. Только полностью прочитанный диапазон подтверждает отсутствие событий. Предзагрузка не переключает видимые даты и не вытесняет работу пользователя.

## Исходные измерения

На семи календарях, пяти списках, 144 задачах и 31 событии медиана трёх серий полной последовательной загрузки составила 10,37 с, параллельного прототипа с четырьмя чтениями — 4,08 с. Обновление всех задач занимало 4,50 с; его ожидание после точного GET одной задачи избыточно.

Подробности, границы измерений и источники: [исследование](performance-research-2026-10-10.md). Это исследовательские результаты, а не замеры новой production реализации. Фактическая плавность прокрутки требует ручной проверки владельцем; синтетические проекции и время синхронизации native clip не равны FPS.

После внедрения первых двух этапов выполнены три read-only серии новой production загрузки на 2026-10-11: 3,903 / 3,164 / 3,251 с, медиана 3,251 с. Объём: семь календарей, пять списков, 146 задач, 31 событие, 14 вызовов. Чтение одного списка: 0,832 / 0,761 / 0,843 с, медиана 0,832 с, один вызов вместо прежних шести. Это три наблюдения в текущей сети, не p95 и не гарантированная задержка; исходный baseline снят в другой серии и имел 144 задачи.

Воспроизводимая команда: `rtk proxy ./scripts/benchmark-gws.sh --live-read-only`. Измеритель не поддерживает записи, не изменяет пользовательский кэш и выводит только числовые метрики; идентичности и содержимое остаются в памяти. Сетевой запуск требует уже настроенной gws авторизации.

## Проверка реализации

Синтетические fixtures должны подтверждать immediate/idempotent merge, узкую область удаления, перенос с новым ID, защиту от устаревших ответов, объединение областей сверки, предел параллельности, последовательную пагинацию, сохранение данных при ошибке, повторное открытие кэшированной недели и неизменность текущего диапазона при предзагрузке.

Из корня репозитория выполнить `rtk proxy ./scripts/test.sh`, `rtk proxy ./scripts/test-native-ui.sh`, `rtk proxy ./scripts/build-app.sh`. Сборка создаёт `dist/g-calendar.app`; успешная сборка не означает ручную UI приёмку. Каждый логический этап коммитится после проверок, отправка main выполняется без переписывания истории.

## Статус

План одобрен пользователем 2026-10-11. Первые три этапа реализованы: verified merge до callbacks, read-only payload без фонового commit, revision/freshness guard, максимум четыре чтения, targeted списки/календари и metadata-only сверка списка. Кэш хранит пять диапазонов; TTL сверки диапазона пять минут, metadata календарей 15 минут. Предзагружается одна следующая полная неделя без цепочки загрузок. Безопасный завершённый full принимается при навигации, затем читается только оставшийся календарный диапазон. Model suite: 638 assertions; сборка приложения успешна. Отмена gws останавливает последующие страницы и коллекции; уже запущенный процесс ждёт ответа или timeout. Реальные записи и ручная прокрутка не проверялись. UI оптимизация — следующий этап.
