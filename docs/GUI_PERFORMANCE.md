# Измерение локального интерфейса

`DemoPerformanceProbe` включается только совместными аргументами `--demo --profile-ui`. В normal, ledger и notification режимах он не создаёт файлов, observers или timers. Пробник не выполняет UI-действий, не читает пользовательские данные и не вызывает gws или уведомления.

## Что измеряем

- `launch`: начало пробника → первый update видимого окна. Это часть запуска после инициализации пробника, а не время от старта процесса или холодного запуска macOS.
- Категории локальных действий: вызов `begin` перед изменением состояния → ближайшая `NSWindow.didUpdateNotification` видимого окна приложения. Соседние старты одной категории до update объединяются; это отражено `coalesced_starts`.
- Возможность работы главного RunLoop: repeating Timer с периодом 20 ms, нулевым tolerance и режимом `.common`. В активном приложении задержка равна `max(0, текущий_tick − предыдущий_tick − 20 ms)`. Фоновое/свёрнутое окно исключено. Это задержка планирования с влиянием macOS, нагрузки и самого измерения; она не доказывает причину задержки.
- Размер content viewport в points и backing scale, число наблюдений, среднее, p50/p95/max. Percentiles вычисляются по ограниченному последнему окну до 8192 наблюдений; lifetime count/mean/max сохраняются.

`NSWindow.update()` сам по себе публикует уведомление на проходе AppKit event loop. Оно **не доказывает завершение SwiftUI layout, отрисовку содержимого или показ pixels compositor**. Метрики не являются FPS, GPU timing, scroll smoothness или полной задержкой сети. Время ответа Computer Use в них не включено. Приёмка содержимого и плавности остаётся отдельной визуальной проверкой.

## Приватный отчёт

Пробник создаёт новый абсолютный каталог `g-calendar-ui-profile-<случайный UUID>` в системном временном каталоге с режимом `0700`, файл `report.json` с режимом `0600`. Он печатает путь `G_CALENDAR_UI_PROFILE_REPORT=…` только в opt-in режиме. JSON содержит allowlist категорий, агрегаты времени/числа наблюдений и viewport; названия, ID задач/событий, поисковые строки и координаты действий отсутствуют. Запись выполняется вне главного потока и заменяет файл атомарно. Снимок пишется после update с ограничением частоты и каждые пять секунд активного sampling; `flush()` запрашивает свежий снимок. Завершение через SIGTERM может оставить последний уже записанный снимок.

## Подключение hooks

Все вызовы выполняются на MainActor. До показа первого окна:

```swift
DemoPerformanceProbe.shared.startIfRequested(arguments: ProcessInfo.processInfo.arguments, mode: launchMode)
```

Перед локальным state mutation, в Button action/Binding setter или методе модели, но не внутри `View.body`:

```swift
DemoPerformanceProbe.shared.begin(.section)
// Затем меняется section.
```

Категории: `.section`, `.search`, `.selection`, `.range`, `.filter`, `.taskList`, `.form`, `.taskCompletion`, `.appearance`. Resize наблюдается самим пробником. Hook в SwiftUI `.onChange` после изменения обозначает уже начало реакции, а не начало пользовательского ввода, поэтому для search предпочтителен Binding setter. `.form` нужно вызывать непосредственно перед открытием sheet. Метод ничего не делает без opt-in.

## Протокол приёмки

1. Запустить оптимизированный актуальный `.app` с `--demo --profile-ui`; записать дату, сборку, macOS, оборудование, число fixture задач/событий, viewport и scale отдельно в документ проверки.
2. Через Computer Use выполнить по минимуму десять повторений нужных действий с паузой на визуальное подтверждение. Проверить поиск, календарь/задачи, даты/режимы, фильтры/списки, формы и изменение размера. Не смешивать cold launch и повторные действия.
3. Прочитать последний private JSON после завершения серии и остановиться, когда counts отражают сделанные операции. Pending операции не считать завершёнными. При малом sample count p95 не использовать как надёжную оценку.
4. Сопоставить агрегаты с визуальным результатом, записать окружение и границы измерения. Бюджет задать после фактического baseline. Для pixel latency, GPU frames и attribution stalls потребуется отдельный инструмент Instruments/профилировщик.

Официальные источники: [NSWindow.update()](https://developer.apple.com/documentation/appkit/nswindow/update()), [NSApplication.updateWindows()](https://developer.apple.com/documentation/appkit/nsapplication/updatewindows()), [Timer](https://developer.apple.com/documentation/foundation/timer), [RunLoop.add(_:forMode:)](https://developer.apple.com/documentation/foundation/runloop/add(_:forMode:)).

## Проверка реализации, 6 октября 2026

Focused `swiftc -typecheck` с project toolchain, AppKit и deployment target macOS 13 прошёл. Одноразовый compiled harness проверил шесть отрицательных комбинаций: normal с обоими флагами, demo без любого из двух флагов, ledgerAcceptance, notificationTest и syntheticAcceptance с обоими флагами. Во всех случаях запуск вернул `nil`; `begin`/`flush` оставались инертными. Harness не открывал окон и удалён после проверки. Эти проверки подтверждают gating, а реальные timing/resize/permissions измеряются отдельно в текущем demo GUI запуске.

## Фактический baseline — 7 октября 2026

Оптимизированная сборка run-48822, macOS 27.0.1, Apple M4 Pro, 24 GiB, scale 2. Синтетический набор: 51 задача, 10 событий, два календаря и два списка. Проверены окна 761×561 и 1434×897 content points. Действия выполнялись Computer Use, данные пользователя и сеть отключены. [JSON агрегаты](gui-performance-baseline.json) не содержат названий, ID или поисковых строк.

| Выбор строки | 11 | 12,98 | 15,75 | 30 |
| Поиск | 12 | 41,90 | 132,00 | 200 |
| Фильтр | 10 | 111,70 | 184,45 | 250 |

Это исходные ориентиры регрессии на этом наборе и оборудовании, а не гарантии для произвольного объёма данных. Малые n делают p95 приблизительным. Launch имеет только одно наблюдение 492,58 мс после старта пробника; предел 1000 мс — предварительный ориентир, холодный процессный launch не измерен. При resize объединено 180 стартов; это последовательность событий изменения размера окна.

Schema 2 измеряет `.scroll` отдельно: длительность синхронного обработчика bounds native clip, включая синхронизацию оси/заголовков. Десять чередующихся AX Scroll Up/Down дали 242 bounds callbacks. Это не задержка до показа пикселей. В schema 1 ожидание didUpdate могло включать простой после прокрутки (23 секунды); ошибочная метрика исключена из operations baseline и не использована для бюджета. Это исправление измерителя, не обнаруженный UI stall.

RunLoop p95 задержки планирования 0,94 мс, max 598,76 мс; 119 задержек >50 мс и 71 >100 мс на всей серии. Источники смешаны: системные меню, анимация sheets, автоматизация и приложение. Без Instruments/xctrace нельзя приписать их конкретной функции. Самые долгие измеренные действия — формы и resize; по малой выборке менять их архитектуру оснований нет. Предварительный RunLoop p95 ориентир ≤5 мс.

Три idle snapshots собственного PID: CPU 0,4/0,6/0,5%, RSS 203968 KiB (199,2 MiB). Ориентир на данном demo: idle CPU ≤2%, RSS ≤300 MiB. Peak CPU/RSS, FPS, GPU и compositor timing не измерены. Оптимизированные model fixtures измеряют отдельно 4096 задач и 1024 перекрывающихся события; эти цифры не выдаются за GUI показатели или сетевые задержки.
