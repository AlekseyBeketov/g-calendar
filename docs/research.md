# Техническая feasibility: g-calendar для macOS

Срез источников и локальной среды на 2026-10-01. Факты отмечены как источниковые или локальные; архитектурные выводы — оценка для этого MVP, не гарантия реализации.

## Рекомендация

**Выбрать Swift + SwiftUI для основного интерфейса и lifecycle приложения, Foundation для модели/сети, `UserNotifications` для локальных напоминаний; подключать AppKit точечно, когда SwiftUI API недостаточно.** `gws` использовать первым read-only адаптером через `Process`, строго с allowlist команд чтения и argument vector (без shell); не читать его credentials/tokens, не экспортировать их, не запускать команды авторизации. Это лучше соответствует единственной целевой платформе, системным уведомлениям и standalone `.app`, чем добавление WebView и Rust в MVP. Apple называет SwiftUI предпочтительным выбором для новых приложений и документирует интеграцию SwiftUI/AppKit; точечный AppKit bridge — нормальный вариант.[6]

**Оговорка по сборке:** SPM пока нельзя считать подтверждённым путём. Во время disposable feasibility-пробы `swift build` завершился ошибкой линковки манифеста `PackageDescription.Package` (symbol `swiftLanguageVersions...`); ошибка воспроизводится и на стандартном проекте, созданном `swift package init`, и с manifest tools version 6.4. Это локальная проблема инструментария/манифеста, а не доказательство невозможности SwiftUI. Отдельная проба `swiftc` с текущими CommandLineTools успешно собрала SwiftUI binary; корректный `.app` bundle был собран и запущен. Следующий engineering gate — coder должен найти безопасный воспроизводимый build/test workflow, проверить SPM work-around, а если он не работает — использовать/документировать прямой `swiftc` путь без заявления успешного `swift build`.

Tauri — разумная альтернатива, если появится реальная потребность в переиспользовании web UI или кроссплатформенности. Для macOS desktop Tauri допускает Xcode Command Line Tools, но требует Rust; локально `cargo`/`rustc` отсутствуют. Tauri использует HTML в системном WebView и Rust backend с JS↔Rust мостом: это добавляет стек, не давая MVP преимуществ нативного SwiftUI.[10] SwiftPM-сбой надо исследовать отдельно; переход на Tauri сейчас не устраняет локально подтверждённый дефицит Cargo.

## Факты и границы MVP

- **Google Calendar: квоты и стоимость.** На текущей странице указаны лимиты 10 000 запросов/минуту на проект и 600/минуту на пользователя в проекте; действует скользящее окно. Суточный порог — 1 000 000 запросов/проект. На дату проверки обычное использование описано как без доплаты, но списание за превышение квот запланировано позднее в 2026 году; полные условия обещаны отдельно, с уведомлением минимум за 90 дней.[1] Google объявил переход с 2026-05-01: новые квоты раскатывались для новых проектов, а проекты, использовавшие API в ноябре 2025 — апреле 2026, сохраняли прежние квоты как минимум 60 дней.[2] Этот минимальный период уже прошёл; точная квота зависит от Cloud project, а cohort существующего `gws` проекта здесь не установлен. **Вывод:** не обещать «навсегда бесплатно»; ограничить частоту синхронизации, кэшировать, обрабатывать 403/429 с exponential backoff и перед масштабированием проверять quota конкретного проекта. Новая платная инфраструктура для MVP не требуется.
- **Google Tasks — due не содержит времени.** `due` принимает RFC 3339 timestamp, но API сохраняет только дату: время при записи отбрасывается и прочитать/записать due-time нельзя.[3] В UI показывать Google task как date-only; точное локальное напоминание — отдельное local-only поле приложения с ясной маркировкой, без обещания синхронизации этого времени с Google. Google Calendar, напротив, имеет start/end с временными зонами и list-параметр `singleEvents`, который умеет разворачивать повторяющиеся события в экземпляры.[4]
- **Текущий безопасный адаптер.** По предоставленному владельцем подтверждению уже работают `gws auth status`, `gws calendar calendarList list`, `gws tasks tasklists list`; существующая авторизация имеет Calendar/Tasks scopes. Повторная авторизация не нужна. `gws` отдаёт структурированный JSON и динамически строит команды по Google Discovery, но README прямо предупреждает, что это не официально поддерживаемый Google продукт и проект до v1.0 активно развивается с возможными breaking changes.[9] Пусть приложение вызывает только разрешённые чтения (calendar list/events list, tasklists/tasks list), контролирует exit code, stderr, JSON и pagination; не считайте ошибку пустым результатом. Укажите известный абсолютный путь как локальный default/настройку, а не полагайтесь на PATH GUI-процесса. CLI discovery/network/version — дополнительная точка отказа; закрепляйте поддерживаемую версию и тестируйте обновления. API scope самого CLI может быть шире запрета в UI, поэтому allowlist должна быть на границе адаптера.
- **Native OAuth — только для будущего отдельного клиента.** Для desktop/macOS Google рекомендует OAuth тип Desktop app и loopback IP redirect через системный браузер; установленный клиент не может хранить секрет как надёжную тайну, PKCE следует применять.[6] Сейчас не создавать/не экспортировать credentials и не запускать consent flow. Если позже перейти с `gws` на собственный прямой клиент и распространять его другим людям, потребуются отдельный Google Cloud OAuth setup и оценка верификации чувствительных scopes; требования зависят от scopes и аудитории.[7]
- **Локальные уведомления.** `UNUserNotificationCenter` поддерживает планирование local notifications на macOS. Приложение должно просить разрешение в понятном контексте, читать актуальные настройки и только затем планировать/обновлять/отменять уведомления; пользователь может изменить разрешения и тип доставки.[8] Это локальные уведомления, не Google Tasks alarm и не гарантия «будильника»/доставки в обход настроек ОС. Google Calendar push для изменений требует HTTPS webhook receiver и notification channel; без hosted backend не включать его в MVP.[5]
- **Функциональный MVP:** read-only списки календарей, событий в выбранном диапазоне и Task lists/tasks; недвусмысленные loading/empty/error/stale состояния, pagination, поиск/фильтрация; month/week/day или agenda view; date-only для Tasks; опциональные пользовательские локальные напоминания с разрешением. Повторяющиеся Calendar events считать поддержанными лишь после проверки `singleEvents=true`, пагинации и границ временной зоны. Не заявлять полную Google parity, запись/завершение задач, двустороннюю синхронизацию, Tasks due-time, Google push или recurrence для Tasks, пока соответствующий механизм отдельно не реализован и не проверен.
- **ETasks — только UX-наблюдения:** единый список задач, календарные week/month представления, поиск, dark mode, favorites, локальные alarms — полезные ориентиры уровня паттернов, но это сайт продукта для Apple-платформ, не API-спецификация. Не копировать тексты, изображения, иконки или иные ресурсы; не переносить в MVP обещания продукта, не обеспеченные API/реализацией.[12]

## Сборка и распространение

Локально проверено: macOS 27 arm64; Swift 6.4; активный developer directory — `/Library/Developer/CommandLineTools`; `xcrun --find notarytool` доступен. `xcodebuild -version` в текущем выборе инструментов завершается ошибкой: активен пакет Command Line Tools, не полный Xcode. Это не подтверждает наличие полного Xcode в другом месте. `cargo`/`rustc` не найдены. `swift build -c release` не является подтверждённой командой данного проекта: проба SPM завершилась описанной выше ошибкой манифеста. Поэтому пока не публиковать рецепт успешной сборки `.app`; проверить прямой `swiftc`, корректный bundle identifier/`Info.plist` и запуск staged `.app` как отдельную инженерную задачу. `notarytool` доступен, но его наличие не означает, что приложение подписано или готово к notarization.

Для публичного распространения вне Mac App Store Apple требует Developer ID signing и notarization по актуальному guidance; для локальной отладочной сборки это не этап. Notarization требует корректной подписи и подготовленного пакета.[11] Здесь никаких подписей, credentials Apple, notarization submissions или релизов не выполнялось и не разрешено.
