# Время Google Tasks: начало работы, дедлайн и синхронизация

Проверено 12 октября 2026, Europe/Moscow. Исследование относится к g-calendar. Использованы Context7, TinyFish, официальные документы, публичные API Discovery schemas, разрешённый synthetic Google Tasks эксперимент и затем явно разрешённый computer-use Google Calendar. Создана отдельная тестовая доска с одной задачей, проверена через API и изменена через Google UI; данные оставлены для проверки владельцем. Браузерные cookies не копировались. После отдельного конкретного разрешения пользователя существующие gws OAuth-данные использованы только в памяти для read-only private API probe; секреты не выводились и не сохранялись.

## Что означает время в Google

В актуальном интерфейсе Google Calendar задача может иметь **начало и окончание работы**. Это резервирование времени для выполнения задачи, а не дедлайн. Отдельный **Deadline** задаёт дату, к которой задача должна быть завершена, и показывается в области событий на весь день. Для повторяющейся задачи справка не допускает отдельного времени окончания.[1]

Например, «подготовить отчёт» можно запланировать на 14 октября, 15:00–16:00, а дедлайн задать 16 октября. Уведомление о запланированной работе Google описывает как уведомление на назначенную дату/время. Отдельное напоминание о дедлайне приходит в 09:00 дня дедлайна. Это две разные семантики, их нельзя объединять в одно поле.[1]

Google официально анонсировал time blocking задач в ноябре 2025. Задача остаётся в списке задач и одновременно занимает временной интервал в календаре. Анонс описывает возможности интерфейса, а не доступный сторонним клиентам API-контракт.[2]

По уточнению Лехи g-calendar не должен уведомлять задачи без точного времени и события на весь день. Google-вариант напоминания в 09:00 не переносится в g-calendar.

## Проверка публичного API по свежей схеме

Скачана публичная схема без авторизации:

    https://tasks.googleapis.com/$discovery/rest?version=v1

Фактическая ревизия схемы: **20261011**. SHA-256 полученного файла:

    5958c39eb18c2c1aa7189a5dc16c23a0777e50eb229f13b74ce6bcbe7c840529

У ресурса Task 17 полей: assignmentInfo, completed, deleted, due, etag, hidden, id, kind, links, notes, parent, position, selfLink, status, title, updated, webViewLink. Отсутствуют startTime, startDateTime, endTime, duration, deadline, deadlineTime, dueTime и reminders. Проверка опирается на полный список полей, а не на отсутствие конкретного имени в поисковой выдаче.

Схема и документация определяют `due` как запланированную **дату** задачи, то есть день работы/отображения в календаре. Документация прямо отличает его от дедлайна и сообщает, что время при записи отбрасывается, а прочитать или записать scheduled time через API нельзя.[3]

Следовательно, вывод «передадим ISO timestamp в due — Google запомнит час» неверен. Поля completed и updated содержат моменты времени, но относятся к завершению/изменению; использовать их как время начала тоже неверно. Обновление SDK, transport gws на REST и дополнительный OAuth scope не добавляют полей, отсутствующих в контракте сервера.

Схема Calendar API получена отдельно:

    https://www.googleapis.com/discovery/v1/apis/calendar/v3/rest

Ревизия: **20261005**, SHA-256:

    328644cd3a76ede1883431f0cbbd4aa520cf439de7a75b673b6873eb2d016755

У Event нет документированных task/deadline/duration полей, а описание eventType перечисляет birthday, default, focusTime, fromGmail, outOfOffice и workingLocation. Тип task не указан.[4] Это не доказательство отсутствия любых технических связей между Calendar и Tasks: нужно отдельно проверить, возвращает ли events.list временной блок реальной тестовой задачи и существует ли надёжная связь по ID. Такая проверка ещё не выполнялась. Сопоставление только по названию и дате недостаточно: две задачи могут иметь одинаковое название, а даты могут отличаться от дедлайна.

## Что проверено из альтернатив

| Путь | Результат | Может обеспечить именно Google task time sync сейчас? |
| --- | --- | --- |
| Публичный Tasks REST API | Свежая схема и документация исключают время | Нет |
| Google Apps Script Tasks service | Использует те же объекты/методы/параметры публичного API | Нет дополнительного доступа |
| Calendar REST events | Есть точное время событий, нет документированной модели Task | Связь временного блока с задачей пока не проверена |
| Google CalDAV | Официально не поддерживает VTODO/VJOURNAL | Документированного доступа к Tasks через VTODO нет |
| Google Takeout | Архив содержит больше task metadata, например recurrence и порядок списков | Экспорт для исследования, не доказанный двусторонний online sync |
| Внутренний веб-сервис Google Tasks | В актуальной веб-сессии подтверждены чтение времени и запись Google UI | Протокол подтверждён; самостоятельный доступ нашего OAuth-клиента пока не работает |
| Локальное время задачи | Можно реализовать внутри g-calendar | Не отвечает требованию синхронизации с Google |
| Время в notes или отдельное событие | Собственные metadata/сущность | Не меняет настоящее время Google Task |

Apps Script прямо объявляет совпадение схемы с публичным API.[5] CalDAV прямо исключает VTODO.[6] Takeout перечисляет due dates, recurrence, list order и прочие metadata, но не предоставляет через эту справку контракт непрерывной записи обратно. Поддержка scheduled time в конкретном архиве и его формат без реального export не доказаны; отсутствие слова time в справке нельзя считать доказательством его отсутствия в файле.[7]

## Внутренний сервис: конкретный след и границы доказательства

В опубликованной автором записи DevTools за январь 2024 описан запрос Calendar Web к:

    tasks-pa.clients6.google.com/$rpc/google.internal.tasks.v1.TasksApiService/Sync

Формат запроса указан как application/json+protobuf; запрос происходит в контексте веб-сессии с cookies и заголовками клиента. Автор не реализовал и не декодировал этот протокол. Это первичное наблюдение исследователя, но не документация Google и не подтверждение рабочего поведения на октябрь 2026.[8]

Поиск публичных исходников по TasksApiService, google.internal.tasks.v1 и tasks-pa не обнаружил проверенного клиента, который одновременно читает и записывает scheduled time. GitHub code search без входа ограничен; отсутствие индексируемого результата не доказывает, что таких клиентов не существует. Рассмотренный OAuth-клиент TaskMenu работает с обычным due и не даёт нужного обхода.[9]

Нельзя на основании URL Sync объявлять, что он возвращает время, что он позволяет запись или что обычный OAuth bearer g-calendar для него подходит. Нельзя угадывать private mutation method и пробовать его на пользовательских задачах. Нужно наблюдать актуальный запрос/ответ web UI для одной тестовой задачи и сопоставить значения с действиями.

Первоначальный вывод до computer-use: Google хранит и синхронизирует время в своих клиентах, но публичный Tasks API не открывает эту часть модели. Последующий разрешённый эксперимент подтвердил конкретные поля времени и deadline во внутреннем протоколе — см. раздел ниже. Точная архитектура базы данных Google не исследована; наблюдаются сообщения сервиса, а не устройство хранилища.

## Подтверждённый внутренний протокол в веб-сессии 2026

Леха затем явно разрешил computer-use и работу с установленным веб-приложением календаря. Найден уже авторизованный Chrome/PWA Google Calendar. Для сохранения открытого пользователем редактора создана отдельная исследовательская вкладка. Все изменения ограничены ранее созданной доской `[g-calendar TEST deadline b58c6440f6]` и её единственной synthetic задачей.

В интерфейсе Tasks задаче установлено **14 октября, 18:17 Europe/Moscow**, что соответствует **15:17 UTC**. После сохранения и полной перезагрузки web UI снова показал 18:17. Повторный обычный Tasks GET по-прежнему вернул date-only due=2026-10-14T00:00:00.000Z: публичная и внутренняя модели действительно различаются.

Через DevTools наблюдались два актуальных маршрута. Запись времени из Tasks fullscreen отправилась на `tasks.google.com/_/TasksWebEmbedUi/data/batchexecute`, RPC `SOV0tb`. В `f.req` были явные массивы `[2026,10,14]`, `[18,17]`, строка `Europe/Moscow` и timestamp `1791991020`. Это наблюдённый запрос изменения, а не гипотеза о поле. Значение CSRF-параметра `at` не сохранялось в отчёт или исходники.

Чтение в календаре выполняет `tasks-pa.clients6.google.com/$rpc/google.internal.tasks.v1.TasksApiService/Sync`, content type `application/json+protobuf`. Сохранён очищенный HAR ровно одного такого чтения, HTTP 200. Его ответ содержит synthetic задачу с тем же точным временем. В наблюдённой flattened Task-модели scheduled datetime находится в zero-based поле `task[8][0]`:

    [null, [2026,10,14], [18,17], "Europe/Moscow", null, ["1791991020"]]

Unix seconds здесь сериализованы строкой. Это сообщение json+protobuf, не обычный REST JSON с именованными полями; нумерацию нужно проверять parser fixtures и неизвестные поля сохранять. Позиция объекта в корневом списке (например, 112) не является контрактом; искать по identity.

Проверено на synthetic задаче: её публичный Tasks ID равен base64url-кодированию внутреннего 16-символьного Task ID. Это надёжнее сопоставления по заголовку для данной проверенной identity. Не объявлять преобразование универсальным для всех разновидностей Google Tasks до проверки assigned/recurring/moved tasks. Боевые IDs в отчёте заменены aliases.

В календарном редакторе у этой же задачи отдельно выбраны окончание **19:04** и **«Срок сдачи» 15 октября**. Сохранённый UI показал интервал 18:17–19:04. Sync-запись получила HTTP 200 и вернула updated Task с отдельным deadline в `task[1][18]`:

    [null, [2026,10,15], null, "Europe/Moscow", null, ["1792011600"]]

Поле времени deadline равно null; timestamp соответствует полуночи даты в указанной зоне. Форма Google давала дату срока, но не время этого срока. Следовательно, нельзя представлять scheduled 18:17 как время поля Google Deadline. Time block появился отдельно в `task[23]` со ссылкой на календарную сущность. Точный GET по наблюдённой ссылке через обычный Calendar REST вернул 404; это не доказывает отсутствие любых иных mappings, но данный прямой способ не сработал.

Начало 18:17 проверено после полной перезагрузки отдельным Sync-чтением. Deadline и time-block проверены по сохранённому UI и server response на запись; дополнительная независимая browser-проверка после последней перезагрузки не завершена: browser tool сообщил, что пользователь отклонил доступ к calendar.google.com. Другие browser surfaces для обхода отказа не использовались. Скриншот конечного результата сохранить не удалось до остановки browser access; готовность UI приложения g-calendar не проверялась.

Снимки находятся в `.hermes/research/task-time/tasks-sync-after-time.har` и `tasks-sync-with-deadline.har`; очищенные synthetic-only структуры — в `synthetic-time-read-evidence.json` и `synthetic-deadline-read-evidence.json`. Проверено отсутствие Authorization/Cookie/Set-Cookie в этих HAR. Исходные ответы содержат другие task metadata аккаунта, поэтому весь каталог локальный и игнорируется Git; в документацию переносятся только synthetic значения и описания схемы.

## Прямой доступ приложения: фактический OAuth-результат

Первую попытку такого probe автоматический reviewer отклонил: экспорт unmasked OAuth secrets и передача Bearer на недокументированный endpoint не были прямо разрешены. Леха затем отдельно подтвердил именно этот способ. После подтверждения использованы существующие client_id/client_secret/refresh_token gws в памяти, выполнен штатный refresh, затем отправлен только наблюдённый **read-only** Sync payload. Browser cookies не извлекались. Задачи этот probe не меняет.

Google ответил HTTP 403. После разбора error в формате json+protobuf получено сообщение: **Tasks Private API не использован ранее или отключён в проекте OAuth-клиента**. Google указал страницу включения `tasks-pa.googleapis.com` в Cloud Console. Номер проекта намеренно не публикуется.

Это более узкий результат, чем «Google запрещает любой OAuth»: данному OAuth-клиенту сервис сейчас недоступен/не включён. Нельзя объявлять невозможность OAuth без проверки включения сервиса; также нельзя обещать, что стороннему проекту разрешат включить закрытый API. Автоматического включения сервиса, изменения IAM, OAuth scopes или Google Cloud настроек не выполнялось.

Для HTTP 403 рассмотрены пять направлений: включён ли сервис в проекте consumer, доступны ли проекту private API/allowlist, нужны ли дополнительные scope, нужны ли frontend API key/client headers и допускается ли только web-session auth. Выбран следующий шаг с наибольшей доказательной ценностью: проверить доступность **именно tasks-pa.googleapis.com** для проекта нашего OAuth-клиента. Реальный error указывает на этот слой; смена timestamp/payload или слепой повтор запроса проблему не доказывают и не решают.

Публичный поиск не дал официального руководства подключения Tasks Private API сторонним проектам. Найдена только непроверенная поисковая зацепка Issue Tracker о PERMISSION_DENIED при попытке его включения; страницу не удалось прочитать, поэтому она не является подтверждением запрета для нашего проекта.

Для полноценной самостоятельной синхронизации остаётся получить разрешённый канал: private API в нашем OAuth-проекте, если Google допускает доступ, либо отдельный transport внутри авторизованной Google web session. Второй путь меняет способ входа и поддержку приложения; он не должен молча копировать cookies браузера или выдавать browser automation за штатный REST. Точное read/write время в клиенте g-calendar пока не реализовано и не проверено.

## Эксперимент, который даст ответ

Изначально пользователь отклонил браузерный эксперимент и разрешил только тестовую доску через API. Позже он прямо разрешил computer-use; выполненные результаты приведены выше. Последняя попытка чтения browser state отклонена browser tool, поэтому дальнейшее управление браузером требует восстановления доступа. Cookies не извлекать. Описание ниже задаёт оставшиеся проверки собственного transport, а не заменяет явное разрешение действий.

Сначала создать доску `[g-calendar research task-time]` и одну задачу с уникальным названием. Задать начало на будущую дату в 15:17, окончание 16:04 и дедлайн на следующий день. Не использовать совпадающие даты: тогда невозможно отличить scheduled day от deadline. Точные временные значения выбираются, чтобы их легко отличить от defaults и rounded значений.

Выполнить публичные task GET и events LIST только в диапазоне тестовой задачи. Проверить возвращаемые поля и связанный event, если он вообще присутствует. Записать только результаты проверок и synthetic значения. Локальные resource IDs нужны для корреляции, но не для публикации отчёта.

Через актуальный веб-интерфейс отдельно изменить start minute, end minute и deadline day. Наблюдать только запросы и ответы сервиса Tasks, относящиеся к synthetic задаче. Авторизацию держать в исходной веб-сессии: cookies, bearer и anti-CSRF tokens не помещать в репозиторий, отчёт или tool outputs. Для воспроизводимых parser fixtures сохранить только обезличенные структуры с synthetic ID и значениями.

Результат чтения считается доказанным, только если можно получить start/end/deadline и стабильную identity задачи, отличить отсутствие времени от ошибки/неполной синхронизации, а изменённое время правильно прочитано после нового запроса и перезагрузки веб-клиента.

Результат записи считается доказанным, только если отдельный клиентский путь меняет start с 15:17 на 15:23 у **той же задачи**, точное повторное чтение подтверждает изменение, перезагрузка Google UI показывает 15:23, а deadline, end time, notes, completion и board membership сохраняются по выбранной семантике. Действие UI само по себе доказывает только работу Google UI, а не собственного transport. Если запись работает лишь через UI, это нужно отдельно назвать browser-assisted sync.

После базового результата проверить timezone/DST, изменение даты, удаление времени, completed/uncompleted и перенос доски. Recurrence — отдельный следующий шаг: не считать поддержку единичной задачи доказательством изменения всей серии и её экземпляров. В конце удалить только созданную тестовую задачу и тестовую доску, проверить отсутствие synthetic объектов.

### Выполненный эксперимент через публичный Tasks API

Пользователь разрешил отдельную тестовую доску/задачу и попросил оставить их для своей проверки. Создана доска `[g-calendar TEST deadline b58c6440f6]` и одна задача «Проверка API: запланировано 14 октября, 15:17 UTC». Она не является реальным дедлайном пользователя; notes явно помечены synthetic.

В tasks.insert отправлен `due=2026-10-14T15:17:00.000Z`. После insert выполнен **отдельный tasks.get**, который вернул `due=2026-10-14T00:00:00.000Z`. Также отдельным tasklists.get подтверждены ID и название тестовой доски. Точное значение времени не сохранилось. Пояснение: 00:00 UTC — сериализация date-only API-поля, а не доказательство полуночного уведомления Google.

Read-back содержал due, etag, id, kind, links, notes, position, selfLink, status, title, updated, webViewLink. Completion=false. В исходном запросе время указано правильно; это подтверждённое серверное отбрасывание времени, а не ошибка декодирования Swift или часового пояса интерфейса.

Локальный ledger, synthetic resource IDs и результаты находятся в `.hermes/research/task-time/public-probe-ledger.json` и `public-probe-evidence.json`; журнал сохраняется до удаления тестовых объектов владельцем. Скрипт `probe_public_task_time.py` запрещает повторный create при существующем ledger, не содержит удаления и поддерживает отдельный read-only recheck. В него не копируются credentials и tokens. Локальное время не установлено: проверялось реальное поведение публичного Google API.

    requested_due: 2026-10-14T15:17:00.000Z
    returned_due:  2026-10-14T00:00:00.000Z
    exact_due_preserved: false
    board_readback_verified: true
    task_readback_verified: true

Эта проверка доказывает отсутствие сохранения времени **через public due**, но не проверяет scheduled time приватного сервиса, новое поле Deadline в Google UI и наличие timed task block в Calendar events API: создать такую задачу публичным запросом не удалось. Не переносить результат date-only задачи на ещё не проверенную модель time block.

## Как это повлияет на g-calendar

Требование Лехи — **обязательная двусторонняя синхронизация настоящего времени задачи с Google**. Пользователь отдельно подтвердил, что local-only deadline его не устраивает. Называние времени начала «дедлайном» не меняет Google-модель: scheduled datetime и date-only deadline необходимо различать. Локальное время, заметка с timestamp и копия события не являются выполнением требования. В уведомлениях применять реально синхронизированное scheduled time; отдельный native Google deadline не имеет проверенной поддержки времени суток. Не считать временные поля недоступными навсегда: внутренний протокол их отдаёт, вопрос теперь в доступе собственного клиента.

Если внутренний transport подтвердится, отделить его от публичного REST адаптера: обычные task поля читаются штатно, а scheduled start/end/deadline — через отдельную проверенную capability. Хранить происхождение и свежесть времени; unknown не превращать в nil, иначе недоступность private API будет выглядеть как снятое время. Namespace и сопоставление identity привязывать к аккаунту и task list; title matching запрещён. Запись выполняется явно и проходит read-back, неопределённость не повторяет mutation.

Авторизация и стабильность — ещё два критерия, помимо парсинга. Если нужен браузерный вход, это меняет UX приложения; не выдавать такой путь за обычный OAuth REST. Если протокол изменится или сессия закончится, показывать недоступность синхронизации времени и сохранять последние подтверждённые значения. Прототип не включается автоматически для всех аккаунтов до этих проверок.

Исследование не требует внедрения OpenResearch CLI или изменения рабочего Git workflow: здесь проверяются схемы и протокол, а не сравниваются вычислительные эксперименты. Публичные исходные схемы сохранены как локальные артефакты в `.hermes/research/task-time/`, который исключён из Git. Коммиты продуктовых фич и сборка не выполнялись.

## Воспроизводимость публичной части

Из корня `/Users/alexbeketov/g-calendar`:

    rtk proxy curl --fail --silent --show-error 'https://tasks.googleapis.com/$discovery/rest?version=v1' -o /private/tmp/tasks-discovery.json
    rtk proxy jq '.schemas.Task.properties as $fields | {revision, taskFieldCount: ($fields|length), taskFields: ($fields|keys), due: $fields.due}' /private/tmp/tasks-discovery.json

Полученный 12 октября результат: revision=20261011, taskFieldCount=17, due.description явно запрещает чтение/запись scheduled time. Схема динамическая: будущая ревизия может отличаться. Для сравнения сохранены hashes исходных снимков; их нельзя использовать как вечный контракт Google.
